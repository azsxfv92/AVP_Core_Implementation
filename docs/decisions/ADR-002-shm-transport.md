# ADR-002: 같은 기계 구간의 전송을 공유메모리로 바꾼다

## 상태

채택 (2026-10-05, W18). 적용 구간: `aeb_node` → `week16_carla_scenario.py` (`/avp/vehicle/target_accel`).
빌드·실행 플래그로 ROS 2 경로와 전환 가능하며, ROS 2 경로는 제거하지 않았다.

## 배경

AVP 파이프라인에서 RT-MW 가 맡기로 한 구간은 셋이고, 그중 **같은 기계 안**인 것은
`aeb_node`(C++) → `week16_carla_scenario.py`(Python) 하나다. 나머지 둘은 데스크탑↔젯슨이라
네트워크가 필요하므로 이번 결정의 범위 밖이다.

이 구간이 나르는 것은 `std_msgs/Float32` 하나(제동 목표 가속도)이고, 20 Hz 로 발행된다.
안전에 직결되는 명령이라 지연과 꼬리가 중요하다고 **가정**하고 시작했다.

## 선택지

| 안 | 내용 | 비용 |
|---|---|---|
| A. ROS 2(DDS) 유지 | 지금 그대로 | 전송 비용이 측정 대상. 미들웨어를 직접 만든다는 프로젝트 목적과 무관해짐 |
| B. **공유메모리 (shm + seqlock)** | POSIX shm 에 고정 크기 슬롯 하나, 시퀀스 번호로 찢김 감지 | 같은 기계 전용. 정리·디스커버리·통지를 직접 만들어야 함 |
| C. pipe / UNIX socket | 커널을 거치는 지역 IPC | 복사 2회. shm 보다 느리고, 네트워크 구간에도 못 씀 |
| D. UDP loopback | 네트워크 스택 경유 | 같은 기계에서 쓸 이유가 없음. 네트워크 구간에서 다시 평가 (W19) |

## 결정

**B를 채택한다.** 구현은 `rtmw/include/shm_channel.hpp` 한 헤더에 들어간다.

- 큐가 아니라 **최신 값 하나**만 유지한다. 제어 명령은 지나간 값이 쓸모없고, 쌓이면 오히려 위험하다.
- 락 대신 **시퀀스 번호(seqlock)** — 쓰는 쪽이 절대 기다리지 않는다.
- **직렬화 없음.** 같은 기계·같은 컴파일러·고정 크기 POD(24 byte). 파이썬 쪽은 `struct` 로 같은 레이아웃을 읽는다.
- 매핑 수명은 `ShmPtr`(`unique_ptr` + 커스텀 deleter)이 책임진다. 이동 전용이라 두 번 해제가 컴파일 단계에서 막힌다.

## 근거 (실측, 2026-10-04~05, 데스크탑 16코어 / Linux 6.8.0-138)

| 측정 | n | p50 | p99 | max | 조건 |
|---|---|---|---|---|---|
| ROS 2 (DDS) 전송 | 597 | **34.0 µs** | 58.4 | 70.7 | 콜백 수신 |
| RT-MW (shm) 전송 | 597 | **0.1 µs** | 0.2 | 0.6 | 바쁜 대기 수신 |
| RT-MW + 5 ms 폴링 | 601 | 2,947.6 µs | 5,400 | 28,293 | 읽는 쪽이 5 ms 주기로 확인 |
| **실사용 (제어 틱 50 ms)** | 1,094 | **45,648.9 µs** | 47,520 | 48,520 | scenario 의 제어 주기에서 사용 |

- 전송만 보면 **중앙값 340배, 최악값 118배** 개선이다. shm 쪽은 `sd 0.0`, 꼬리가 사실상 없다.
- 공통 기준 시각은 `shm` 슬롯의 `stamp_ns` 이고, 두 경로를 **한 프로세스·한 시계**에서 동시에 쟀다
  (`src/accel_latency_probe.cpp`).

## 대가 · 포기한 것

1. **같은 기계에서만 된다.** 젯슨 구간에는 쓸 수 없다.
2. **정리 책임이 생긴다.** 프로세스가 죽어도 `/dev/shm` 의 이름과 값이 남는다. 다음 실행이 이전 실행의
   값을 물려받는 것을 실측으로 확인했다(85 → 86 으로 이어짐). 초기화·unlink 정책이 필요하다.
3. **디스커버리를 직접 만들어야 한다.** 읽는 쪽이 먼저 뜨면 조각이 없다. 지금은 "생길 때까지 재시도"로
   해결했다. ROS 2 가 공짜로 주던 기능이다.
4. **통지 장치가 없다.** 읽는 쪽이 스스로 확인해야 한다. 5 ms 폴링이면 중앙값에 2.9 ms 가 더해져
   **ROS 2 보다 84배 나빠진다.** 전송의 이득을 읽는 방식이 통째로 까먹을 수 있다.
5. **레이아웃 규약을 두 언어에 중복으로 적었다.** C++ 에 `static_assert(sizeof == 24)` 를 걸어 어긋나면
   빌드가 깨지게 했지만, 근본 해결은 바인딩이나 코드 생성(W23)이다.
6. 안전 로직과의 결합: `last_accel_time` 갱신을 shm 경로가 대신 맡아야 한다. 빠뜨리면 **멀쩡히 받는데도
   타임아웃으로 비상 정지**한다. 전송을 바꿀 때 가장 놓치기 쉬운 지점이었다.

## 이 결정이 **틀렸던 부분** — 측정으로 알게 된 것

시작할 때의 가정은 "이 구간은 안전에 직결되니 전송 지연을 줄이면 이득"이었다. **틀렸다.**

소비자(`scenario.py`)가 **50 ms 제어 주기**로 값을 쓰기 때문에, 최종적으로 제어에 반영되는 값의 나이는
**45.6 ms** 이고 그중 전송이 차지하는 몫은 **34 µs (0.07%)** 다. 전송을 340배 빠르게 해도 체감 이득은 없다.

그리고 그 45.6 ms 는 두 20 Hz 타이머의 **위상 차이**가 지배한다. 두 번 실행에서 41.7 ms 와 45.6 ms 가
나왔고(실행 중에는 `sd 381 µs` 로 고정), **시작 시점의 운이 신선도를 정한다.**

## 뒤집는 조건 / 다음 결정으로 넘기는 것

- 소비자가 **이벤트 기반**이 되면(통지 장치 추가) 전송 이득이 그대로 살아난다 → 통지(`eventfd`/futex) 도입을 먼저 평가한다.
- **메시지가 크고 주기가 빠른 구간**(카메라 `CompressedImage` 약 40~50 KB, 10 Hz)에서는 직렬화·복사 비용이 커서
  이득이 클 가능성이 있다. 다음 적용 대상은 이쪽이다.
- 위상 문제는 전송 교체로 못 푼다. **생산자 주기를 올리거나, 소비자를 이벤트 구동으로 바꾸거나, 위상을 맞추는** 것이 답이다.
- 네트워크 구간은 UDP 로 다시 평가한다(W19). 이 ADR 은 같은 기계 구간에만 적용된다.
